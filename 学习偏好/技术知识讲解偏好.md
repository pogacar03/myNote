# 技术知识讲解偏好

## 总体要求

以后讲解 Java 后端、Redis、MySQL、JVM、网络、并发、Agent 等技术知识时，优先采用“完整流程 + 明确主语 + 适中深度”的方式，不要把一个知识点拆得过细、过碎。

## 1. 状态流转必须清晰

讲一个机制时，优先先给出完整流程，让状态变化和执行顺序一眼可见。

例如讲 epoll：

```text
用户程序调用 epoll_create 创建 epoll 实例
        ↓
用户程序调用 epoll_ctl 注册需要监听的 fd
        ↓
内核维护被监听的 fd 和对应事件
        ↓
Socket 发生可读 / 可写事件
        ↓
内核将就绪事件加入 ready list
        ↓
用户程序调用 epoll_wait 获取就绪 fd
        ↓
用户程序处理对应 fd
```

重点是先说明“谁先做什么、接下来发生什么、最终返回到哪里”，避免先讲大量零散细节再让读者自己拼流程。

## 2. 每一步都要有明确主语

尽量避免省略主语的表达。

推荐：

> 用户程序调用 `epoll_wait` 进入等待状态。当 Socket 发生可读事件时，内核将该 fd 对应的事件加入 ready list。之后 `epoll_wait` 返回就绪事件，用户程序再处理这些 fd。

不推荐：

> 调用 epoll_wait，然后等待。发生事件后加入队列，再取出来处理。

后一种说法容易让人分不清到底是用户程序、内核、Socket 还是 epoll 在执行动作。

## 3. 深度适中，以面试能讲清为标准

默认讲到“机制为什么成立、完整流程是什么、关键数据结构或状态是什么”即可。

除非主动追问，否则不要一开始就深入 Linux 内核源码、具体函数调用链、复杂实现细节。

讲解层次优先按照：

```text
先讲整体作用
    ↓
再讲完整执行流程
    ↓
再讲关键机制 / 数据结构
    ↓
最后给面试总结
```

## 4. 不要讲得太细、太碎

减少大量只有一两句话的小段落，也不要为了“通俗”把一个简单概念拆成十几个步骤。

一个逻辑块尽量完整表达一个意思，例如：

> select 调用时，用户程序会把需要监听的 fd 集合传给内核。内核遍历这些 fd 并判断哪些 fd 已经就绪，然后把就绪状态写回结果集合。select 返回后，用户程序还需要再次遍历结果集合，找出真正就绪的 fd 并进行处理。

这种连续表达优先于把每一句都单独拆开。

## 5. 关键名词之间的关系要讲清楚

如果一个问题里同时出现多个角色，需要明确它们各自负责什么，以及它们之间如何衔接。

例如 Reactor 模型：

```text
listen_fd
    ↓ 发生新连接事件
Reactor 监听到事件
    ↓
Acceptor 调用 accept()
    ↓
生成 conn_fd
    ↓
Reactor 继续监听 conn_fd
    ↓ 发生读写事件
Handler 负责 read / write / 业务处理
```

不要只分别解释 Acceptor、Reactor、Handler 的定义，而忽略它们在同一次请求中的状态流转。

## 6. 最后给一个可直接用于面试的总结

每个知识点最后尽量收口成 1～3 句话，方便直接背诵。

例如：

> epoll 通过 `epoll_ctl` 将需要监听的 fd 注册到内核，并长期维护这些监听关系。当某个 fd 就绪时，内核将对应事件加入 ready list；之后 `epoll_wait` 可以直接获取已经就绪的事件，因此不需要像 select、poll 一样每次遍历全部 fd。

## 7. 默认表达风格

- 中文解释优先。
- 技术名词保留英文，例如 `epoll_wait`、`conn_fd`、`Reactor`。
- 语气自然、直接，不故意口语化，也不写成教材式长篇定义。
- 优先使用流程图、表格和连续说明，而不是大量碎片化 bullet。
- 如果用户已经理解某个前置概念，后续直接在这个基础上继续，不重复从零解释。

## 一句话原则

> **先把状态流转讲清楚，每一步主语明确，再补关键机制；深度以面试能讲清为准，不要过细、过碎。**
